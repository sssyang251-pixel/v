# 电商运营数据分析 Agent

一个面向电商运营岗位作品集和面试演示的 Python MVP。上传 CSV 或 Excel 后，项目会计算核心经营指标、拆解商品/渠道/达人表现、判断环比与同比、识别异常，并生成“数据现状 → 问题 → 可能原因 → 建议”的中文报告。

项目采用可追溯的规则与统计方法，不调用外部大模型。每个结论都能回到指标、区间和分组数据，适合在面试中解释分析思路。

## 快速开始

需要 Python 3.10–3.12。先克隆仓库并进入项目目录，然后创建虚拟环境。

```bash
git clone <GitHub 仓库地址>
cd ecommerce-analytics-agent
python -m venv .venv
```

Windows PowerShell：

```powershell
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

macOS / Linux：

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

打开终端显示的本地地址即可使用。首次启动且未上传文件时，页面读取 `data/sample_ecommerce_data.csv` 中的模拟数据。

命令行演示：

```bash
python cli.py --input data/sample_ecommerce_data.csv --start 2025-07-02 --end 2025-07-31
```

输出默认写入 `demo_output/`，包括 Markdown 报告、指标、环比同比、异常清单及各维度明细。该目录已加入 `.gitignore`，分析结果不会被误加入 Git。

重新生成固定随机种子的模拟数据：

```bash
python scripts/generate_sample_data.py
```

运行测试：

```bash
python -m unittest discover -s tests -v
```

## 数据与隐私

- 示例 CSV 是由项目脚本生成的模拟数据，不代表真实店铺或平台数据。
- 上传文件由本地应用读取和分析；当前版本不连接店铺、数据库或外部 AI 服务。
- 不要将真实业务数据、凭证或个人信息提交到公开仓库。`.gitignore` 已排除常见本地环境、日志和输出目录；提交前仍应检查 Git 变更列表。

## 页面功能

- 上传 `.csv`、`.xlsx`、`.xls` 文件，CSV 支持 UTF-8 和常见中文编码。
- 选择分析日期，并按商品、渠道、达人筛选。
- 查看 GMV、订单量、销量、客单价、UV、CTR、CVR、退款率、ROI。
- 查看日趋势、环比/同比、商品/渠道/达人表现和 GMV 变化来源。
- 查看异常日期、触发规则和严重程度。
- 生成并下载中文运营分析报告。
- 查看每项指标的定义、字段识别结果和不可计算原因。

## 数据字段

日期是唯一必填字段。其他字段按实际数据提供，缺少时对应指标显示“不可计算”，系统不会补造数据。

| 标准字段 | 含义 | 常见别名示例 | 用于计算 |
| --- | --- | --- | --- |
| `date` | 日期，必填 | 日期、统计日期、下单日期、支付日期 | 时间筛选、环比同比 |
| `order_id` | 订单唯一标识 | 订单号、订单编号 | 订单量去重 |
| `order_count` | 聚合订单量 | orders、订单数、支付订单数 | 无订单ID时计算订单量 |
| `units_sold` | 销售件数 | quantity、销量、商品件数 | 销量 |
| `gmv` | 成交金额 | 支付金额、销售额、revenue | GMV、客单价、ROI |
| `visitor_id` | 访客唯一标识 | user_id、访客ID、买家ID | UV去重 |
| `visitors` | 聚合访客数 | uv、访客数、商品访客数 | 无访客ID时计算UV |
| `impressions` | 曝光量 | 展现量 | CTR |
| `clicks` | 点击量 | 商品点击数 | CTR、CVR |
| `refund_order_count` | 退款订单数 | refunded_orders、退款订单量 | 退款率 |
| `is_refunded` | 订单退款标记 | 是否退款、退款状态 | 无退款订单数字段时计算退款率 |
| `refund_amount` | 退款金额 | 退款额 | 保留用于扩展分析 |
| `ad_spend` | 广告花费 | spend、投放消耗、投放金额 | ROI |
| `product` | 商品维度 | product_name、sku、商品名称 | 商品分析 |
| `channel` | 渠道维度 | source、流量来源、平台 | 渠道分析 |
| `creator` | 达人维度 | influencer、达人名称 | 达人分析 |

源文件可以使用标准字段或表中的常见中文别名。若两个源字段同时映射到同一标准字段，程序会停止并提示，避免重复计算。

## 指标口径

| 指标 | 口径 |
| --- | --- |
| GMV | 成交金额求和 |
| 订单量 | `order_id` 去重数；没有订单ID时，使用 `order_count` 求和 |
| 销量 | `units_sold` 求和 |
| 客单价 | GMV ÷ 订单量 |
| UV | `visitor_id` 去重数；没有访客ID时，使用 `visitors` 求和 |
| CTR | 点击量 ÷ 曝光量 |
| CVR | 订单量 ÷ 点击量 |
| 退款率 | 退款订单量 ÷ 订单量 |
| ROI | GMV ÷ 广告花费 |

注意：若源数据已按商品、渠道等维度聚合，UV 求和可能包含跨行重复访客。需要严格去重时，应提供访客ID级明细。项目会在报告中提示这一限制。

## 对比和异常逻辑

环比使用“所选区间之前、天数相同的连续区间”。例如选择 7 月 2 日至 7 月 31 日，环比区间为 6 月 2 日至 7 月 1 日。同比使用上年同期。对应区间没有数据或某项指标缺字段时，该项对比不计算。

异常检测至少需要 7 个有效日期，满足以下任一条件时记录：

- 相对区间中位数的稳健 Z 分数不低于 3；
- 相对前一日的变化绝对值不低于 30%。

变化来源使用当前区间与环比区间的分组 GMV 差额，按绝对影响排序。报告中的原因均明确标记为待验证线索，不把相关性写成因果关系。

## 项目亮点

1. **指标可追溯**：集中定义指标口径，不把缺失字段当作 0，也不伪造结果。
2. **兼容两类数据粒度**：订单明细优先按 ID 去重，聚合报表则使用订单量、UV 等汇总字段。
3. **对比条件严格**：只有历史区间和指标都可用时才计算环比/同比，并展示参考区间。
4. **从描述走向行动**：不仅展示指标，还通过维度差额定位变化来源，并生成可验证的运营建议。
5. **规则透明**：异常阈值、指标公式和数据限制在页面及报告中公开，便于业务复核。
6. **完整但轻量**：分析内核、CLI、页面、模拟数据和测试形成闭环，没有引入数据库或复杂服务。

## 五分钟面试演示

1. 打开页面，说明模拟数据包含两年同期和连续月份，因此可以演示环比、同比。
2. 指出九项核心指标，并打开“口径与质量”说明缺字段不会被填成 0。
3. 在“趋势概览”切换 GMV、CVR、退款率，定位近期变化和异常日期。
4. 在“维度分析”依次切换渠道、商品、达人，展示 GMV 变化来源。
5. 打开“运营报告”，按“现状、问题、可能原因、建议”讲出业务闭环。
6. 上传一个删除了 `ad_spend` 列的文件，展示 ROI 自动变为不可计算，说明系统的数据质量意识。

可以这样介绍：

> 我把电商经营分析拆成数据接入、口径标准化、指标计算、历史对比、异常识别、变化归因和运营建议七步。项目既支持订单明细，也支持平台导出的聚合报表。它不会在缺字段时给出看似完整的假结果，而是明确告诉运营人员缺什么、哪些结论可以相信。演示数据中特意加入了渠道流量下降、转化变化和商品退款率上升，用来验证系统能否从指标变化定位到商品、渠道和达人，并形成下一步动作。

## 简历写法参考

**电商运营数据分析 Agent｜个人项目**

- 使用 Python、Pandas 与 Streamlit 搭建电商经营分析工具，支持 CSV/Excel 导入及中英文字段标准化，自动计算 GMV、订单量、销量、客单价、UV、CTR、CVR、退款率、ROI 等指标。
- 建立日期、商品、渠道、达人多维分析及环比/同比机制，仅在历史区间与必要字段可用时计算，避免缺失数据导致误判。
- 基于稳健 Z 分数、日变化阈值和分组 GMV 差额识别异常及主要变化来源，自动输出“数据现状、问题、可能原因、运营建议”报告。
- 设计数据质量提示与指标口径页，兼容订单明细和聚合报表，并通过自动化测试验证核心公式和缺字段场景。

面试时应把简历中的效率提升、准确率或业务结果替换为自己真实验证过的数据，不要写未经测量的百分比。

## MVP 边界

- 不连接店铺、广告平台或数据库，数据由文件导入。
- 不做跨渠道用户去重，除非源数据提供访客ID。
- 不声称自动识别因果关系；“可能原因”是需要结合活动、库存、价格和内容记录验证的线索。
- 不调用外部 AI 接口，报告由透明规则生成。后续可在保留计算引擎的前提下增加大模型解释层。
